# 1.3.8 — Company Search Orchestrated Failover

## Causa raiz
`runSearchInternal` (source `casa_dos_dados`) chamava `searchCasaDosDados`
diretamente, fora do executor de failover da 1.3.6. Um HTTP 403
"Sem saldo para a operação" encerrava a Nova Prospecção mesmo com Kipflow
e Apify conectados, e o erro técnico aparecia para a vendedora.

## Correção
- Novo ponto único: `src/lib/prospecting/company-search-failover.server.ts`
  (`executeCompanySearchWithFailover`) reutilizando **sem duplicar**:
  Provider Registry, `runWithFailover`, `classifyProviderError`,
  `computeHealth`, `getProviderRuntimeConfig`, `provider_credentials`,
  `provider_usage_events`.
- `runSearchInternal` para `source=casa_dos_dados` agora delega ao failover
  quando `jcs_data_engine_enabled` **e** `smart_flow_ui_enabled` estão ON.
  Com qualquer flag OFF, o fluxo legado permanece **intacto**.
- Casa dos Dados: 403 com corpo "Sem saldo …" agora é classificado como
  `insufficient_balance` (status sintético 402), não `invalid_credentials`.
  Outros 401/403 preservam status para classificação correta.
- Kipflow segue como provider 1 quando elegível. Como o adapter atual só
  pesquisa por CNPJ, buscas amplas por filtro disparam
  `unsupported_capability` e o failover pula silenciosamente para o próximo.
- Apify assume automaticamente com `compass/crawler-google-places`
  reaproveitando `buildGoogleMapsInput` — nenhum actor novo criado.
- Deduplicação: CNPJ → domínio → telefone → nome+cidade/UF, com merge
  apenas de campos ausentes.
- Persistência mantém o mesmo shape de `prospecting_results`. Metadados
  técnicos (`provider_used`, `fallback_chain`) gravados em
  `prospecting_searches.params._failover` para o Centro de Diagnóstico.

## Comportamento
| Antes | Depois |
|---|---|
| Casa dos Dados falhava → busca encerrada com erro técnico | Fallback automático Kipflow → CDD → Apify → custom_api → webhook |
| "Casa dos Dados 403 …" exposto ao vendedor | Mensagem amigável genérica; detalhes técnicos só para Admin/SuperAdmin |
| 403 "Sem saldo" = invalid_credentials | 403 "Sem saldo" = insufficient_balance |
| UI acopla provider ao source | Nenhuma menção a provider na Nova Prospecção |

## Providers e ordem
Ordem padrão por capability (`DEFAULT_CAPABILITY_ORDER.company_search`, já
existente): `kipflow → casa_dos_dados → apify → custom_api → webhook`.
A prioridade final vem de `provider_credentials.priority` da organização.
Para a organização JCS, garantir seed:
`kipflow=1, casa_dos_dados=2, apify=3, custom_api=4, webhook=5`.

## Testes automatizados (mocks — sem consumir APIs reais)
`src/lib/prospecting/__tests__/company-search-failover.test.ts` cobre:
1. Kipflow sem CNPJ → pula para CDD.
2. CDD 403 sem saldo → Apify assume.
3. Todos falham → mensagem amigável sem citar provider.
4. Deduplicação por CNPJ com merge.
5. Primeiro provider OK → não chama próximos.
6. Erro de usuário (400) aborta cadeia sem failover.

Testes existentes de `failover-executor` (Release 1.3.6) e
`failover-classifier` continuam verdes — nada foi duplicado nem substituído.

## O que NÃO mudou
ICP Universal, Pré-Score, Score Final, classificação de leads, CRM,
Cadências, Agentes IA, WhatsApp, Evolution API, Agenda, Email, OAuth,
Importações, Billing, Marketplace, adapters (Kipflow/CDD/Apify),

## Riscos e rollback
- Superfície nova é acionada **apenas** com ambas as flags ON. Rollback:
  desligar `smart_flow_ui_enabled` na organização — o `else` do
  `runSearchInternal` executa exatamente o caminho pré-1.3.8.
- Nenhuma remoção de código legado nesta entrega.

## Logs
`logProviderUsage` (já existente) grava fallback_chain e capability
sanitizados. Nenhum segredo em log — o `sanitizeForLog` da 1.3.6 é aplicado.
