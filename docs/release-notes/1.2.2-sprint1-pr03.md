# Release 1.2.2 — Sprint 1 / PR 03
**Módulo:** Smart Prospect Flow — conectar o Enrichment Orchestrator ao fluxo de Prospecção
**Gate:** `jcs_data_engine_enabled` (com a flag OFF nada muda)

## Objetivo
Substituir o pipeline "buscar → enriquecer tudo → classificar → CRM" por
"buscar → pré-score ICP → descartar ruins → enriquecer só promissores/potenciais
→ score final → decisores só se aprovado → CRM", sem tocar em nenhum módulo
operacional.

## Fluxo antigo (flag OFF, permanece intacto)
Busca → Enriquecimento (todos) → Classificação → CRM

## Fluxo novo (flag ON)
Busca → **Pré-Score ICP (grátis)** → Filtro → Planner → Orchestrator (cache-first)
→ Provider (Registry) → Normalização → **Score Final** → Decisores (só aprovados)
→ Persistência → disponível para CRM

## Regras de classificação (contrato)
| Score | Status | Enriquece? | Busca decisor? |
|-------|--------|-----------|----------------|
| >= 80 | promissor  | sim | sim |
| 60..79 | potencial | sim | só se score final >= 80 |
| 40..59 | frio      | **não** | não |
| < 40   | descartado | **não** | não |
| qualquer + desqualificador | descartado | **não** | não |

## Providers e cache
- Providers pagos continuam sendo chamados **exclusivamente** via
  `orchestrator/execution.server.ts` → `registry.server.ts`.

- Empresas classificadas como `frio`/`descartado` **não invocam** o
  orquestrador; economia integral do custo simulado.

## Créditos economizados
Cada empresa `frio` ou `descartado` economiza `assumed_enrichment_cost_cents`
(parâmetro opcional). Os totais por busca são persistidos em
`prospecting_searches.credits_saved`, `credits_spent`, `smart_flow_stats.savings_pct`.

## Compatibilidade
- Flag OFF: `runSmartFlowFn` retorna `{ ok:false, reason:"feature_flag_off" }`
  e não chama providers, orquestrador ou cache. O fluxo antigo (`preliminaryClassify`,
  `classifyUniversal`, prospecção manual) permanece inalterado.
- Flag ON: nenhuma tela consome as novas funções ainda; a chamada é opt-in por
  quem integrar (rota, cron ou script). Comportamento visual atual não muda.
- Nenhum símbolo público antigo foi renomeado ou removido.

## Riscos
- `runSmartFlowBatch` executa sequencialmente para respeitar rate-limit — em
  lotes muito grandes (>200) o tempo de parede cresce linearmente. Concorrência
  controlada fica para PR 04.
- `smart-flow.server.ts` depende de Supabase real; sem mocks nos testes atuais,
  regressões de query só aparecem em execução ponta-a-ponta.
- Persistência de decisores usa `onConflict: prospecting_result_id,linkedin_url`
  — se a tabela ainda não tiver esse unique index, o adapter cai no fallback
  `insert` (pode ignorar silenciosamente falhas de conflito). Adicionar índice
  único fica no backlog.
- UI de filtro visual (Todos/Bom/Potencial/Frio/Descartados) **não foi
  entregue** por conflito no brief ("adicionar filtro visual" vs "NÃO alterar
  UI"). Backend está pronto (colunas indexadas); o filtro entra no PR 04.

## Rollback

2. `DROP` das colunas aditivas de `prospecting_results` e
   `prospecting_searches` (aditivas; sem outras dependências).
3. Excluir os arquivos listados em "Arquivos criados".
4. `enrichment_jobs`, `enrichment_executions` e o pipeline atual permanecem
   intactos.
