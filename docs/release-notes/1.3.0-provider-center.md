# Release 1.3.0 — Central Multi-Tenant de Provedores de Dados

## Objetivo
Permitir que cada organização configure seus próprios provedores de dados (Casa dos Dados, Kipflow, Apify, API REST personalizada, Webhook) sem depender de novo deploy ou alteração de código. Entrega aditiva, protegida por feature flag.

## Feature flag
`app_settings.tenant_provider_settings_enabled` — default `false`. Ativada nesta entrega apenas para a organização JCS. Enquanto OFF, adapters continuam usando fallback legado via variáveis de ambiente.

## Migração aditiva
`supabase/migrations/*_tenant_provider_center.sql`:
- Colunas novas em `provider_credentials`: `last4`, `base_url`, `timeout_ms`, `daily_limit`, `monthly_limit`, `max_concurrent_requests`, `requests_per_minute`, `requests_per_hour`, `last_success_at`, `last_error_code`, `last_error_message`, `created_by`.
- CHECK em `credential_mode` (`organization` | `platform` | `disabled`).
- Índice único `(organization_id, provider)`.
- Policies write restritas a Admin da organização e SuperAdmin.
- Nova `provider_secret_vault` (server-only, sem policies para authenticated/anon; leitura apenas via service role).
- Nova `provider_audit_log` (auditoria administrativa).
- Colunas `available` e `requires_adapter` em `provider_capabilities`.
- Flag `tenant_provider_settings_enabled` em `app_settings`.

## Providers realmente funcionais
Casa dos Dados, Kipflow, Apify (Google Maps · LinkedIn Empresas · LinkedIn Pessoas · Instagram Empresas), Sites Corporativos, API REST Personalizada e Webhook.

## Providers preparados como "adapter em breve"
Apollo, Hunter, Dropcontact, RocketReach, People Data Labs, NeverBounce, ZeroBounce — cards indisponíveis até haver adapter oficial e testado.

## Segurança
- Segredos cifrados AES-256-GCM em `provider_secret_vault`. Nunca voltam ao frontend — cliente só recebe `last4`.
- Vault sem policies para `authenticated`/`anon`; acesso apenas por service role dentro de server functions.
- Chave mestra em secret manager (`PROVIDER_SECRET_MASTER_KEY`).
- Auditoria em `provider_audit_log` grava `credential_source` mas nunca o valor.
- SSRF guard bloqueia `http://`, `localhost`, `127/8`, `10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `::1`, `fc00::/7`, `fe80::/10` e headers proibidos.
- Editar uma integração abre o campo de chave vazio; enviar vazio preserva a credencial atual.

## RLS
- `provider_credentials`: SELECT liberado para membros da org; INSERT/UPDATE/DELETE apenas para SuperAdmin ou Admin da organização.
- `provider_secret_vault`: RLS ativa, zero policies — service role only.
- `provider_audit_log`: SELECT para SuperAdmin, Admin ou Gerente da organização.

## Testes
- `ssrf-guard.test.ts` — 11 cenários (todas as classes bloqueadas + headers).
- `vault.test.ts` — round-trip AES-GCM, mask `last4`, referência determinística, falha com auth tag adulterada.
- Nenhum teste consome créditos reais.

## Compatibilidade
- Nenhum secret existente foi removido.
- Adapters existentes (`casa-dos-dados.server.ts`, `apify.server.ts`, `kipflow.adapter.server.ts`) continuam lendo variáveis de ambiente. `resolveProviderCredential` está pronta para ser adotada pelos adapters em um PR seguinte.
- Flag OFF → comportamento 100% legado.

## Fallback legado
`resolveProviderCredential` retorna `source: "legacy_env"` para Casa dos Dados / Kipflow / Apify quando não há credencial da organização, mantendo `CASA_DOS_DADOS_API_KEY`, `KIPFLOW_API_KEY` e `APIFY_API_TOKEN` como fallback temporário.

## Riscos
- Rotação futura da chave mestra exige re-encrypt do vault (roadmap).
- Custom REST genérico pode não cobrir provedores com autenticação exótica; usar adapter dedicado quando necessário.

## Rollback
`UPDATE app_settings SET tenant_provider_settings_enabled = false;` — a tela nova passa a exibir "Recurso em rollout" e o resolver ignora credenciais próprias, voltando ao fallback legado.

## Como configurar (organização JCS)
1. Configurações → Integrações → Provedores de Dados.
2. Casa dos Dados → Configurar → colar API Key → Salvar → Testar conexão.
3. Kipflow → mesmo fluxo.
4. Apify → colar API Token → Salvar → Testar conexão.
5. Após "Conectado" nos três, o JCS Data Engine passa a preferir as credenciais da organização; se qualquer uma falhar, o resolver cai para o fallback legado automaticamente.
