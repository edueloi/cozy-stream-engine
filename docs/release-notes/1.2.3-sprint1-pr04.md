# Release 1.2.3 — Sprint 1 / PR 04

## Ativação Controlada do Smart Prospect Flow

### Objetivo
Conectar o Smart Prospect Flow (Pré-Score → Enriquecimento condicional →
Score Final → Decisores) ao fluxo real de Prospecção, sem interromper ou
modificar o comportamento das organizações que não estiverem habilitadas.

### Feature flags
- `jcs_data_engine_enabled` — motor server-side (já existente).
- `smart_flow_ui_enabled` — nova, controla a experiência beta na UI.
- Ambas precisam estar `true` para o novo fluxo aparecer/executar.
- Piloto ativado apenas para a organização JCS (slug `jcs`).

### Migrations
- Adiciona coluna `app_settings.smart_flow_ui_enabled BOOLEAN NOT NULL DEFAULT false`.
- Habilita a flag para a organização com slug `jcs`.

### Arquivos criados
- `src/lib/jcs-data-engine/flags.functions.ts` — server fn `getSmartFlowFlags`
  + helper puro `isSmartFlowAvailable`.
- `src/components/smart-prospect-panel.tsx` — painel "Prospecção Inteligente — Beta".
- `src/lib/jcs-data-engine/__tests__/flags.test.ts` — testes do gate de flags.

### Arquivos alterados
- `src/routes/_authenticated.prospecting.tsx` — adiciona a nova aba
  "Prospecção Inteligente — Beta" **condicional** às flags. Nenhuma tela
  existente foi redesenhada; a aba "Nova busca" e o Histórico permanecem
  intactos.

### Wiring
- O painel executa `runSmartFlowBatchFn` (server fn já existente do PR 03)
  sobre buscas já persistidas, em lotes de 25, respeitando:
  - Pré-Score obrigatório antes de qualquer provider pago;
  - `jcs_data_engine_enabled` server-side (dupla proteção);
  - Orchestrator oficial (cache/budget/retry/rate-limit/cancelamento);
  - persistência sanitizada de `enrichment_executions` e
    `prospecting_decision_makers`;
  - meta de "Leads Bons" como condição de parada do lote.
- Nenhuma chamada direta a Kipflow / Apify / Casa dos Dados foi introduzida.

### Fluxo legado
Preservado integralmente. Com qualquer flag OFF, a página de Prospecção
se comporta exatamente como antes: apenas as abas "Nova busca", "Histórico"
e "Integrações" são renderizadas. Nenhum caminho legado
(Leads, CRM, Cadências, Agentes IA, WhatsApp/Evolution, Conversas, Agenda
Google/MS, E-mail Google/MS, OAuth, Voice AI, SIP, Calls, Billing,
Marketplace, Importações, Webhooks, ICP Universal, Catálogo de Produtos)
foi tocado.

### Fluxo inteligente (quando flags ON)
1. Usuário seleciona uma busca existente + produto/ICP + meta.
2. Painel dispara `runSmartFlowBatchFn` em lotes.
3. Para cada resultado: Pré-Score (grátis) → gate → Orchestrator com
   `required_fields: ["decision_makers"]` só para promissores → Score
   Final via `runUniversalIcpEngine("final")` → persistência.
4. Resultados aparecem nas abas Leads Bons / Em revisão / Rejeitados /
   Em processamento / Todos, sem apagar registros anteriores.

### Testes
- Suíte anterior: **62/62** (Sprint 1 PR 02 + PR 03) — mantida.
- Novos: `flags.test.ts` (3 casos) validando que ambas as flags precisam
  estar `true` para o novo fluxo aparecer.
- Cobertura: gate de ativação 100%. Lógica interna do Smart Flow já
  coberta pelos testes de `classifier`, `metrics` e `gate` do PR 03.

### Consumo de créditos
Nenhum crédito real consumido em automação. O painel apenas invoca
server fns já protegidas por `jcs_data_engine_enabled`, cache e budget.

### Riscos restantes
- UI mínima nesta fase: filtros avançados por decisor/WhatsApp/CNAE ficam
  para o próximo PR.
- Cancelamento distribuído do lote em execução ainda é feito quebrando o
  loop no cliente entre chunks; `cancelPlan` por execução continua
  disponível server-side.
- Importação de "Leads Bons" continua manual pelo fluxo legado
  (`importResults`), como exigido.

### Rollback
Instantâneo via `UPDATE public.app_settings SET smart_flow_ui_enabled = false`
ou `jcs_data_engine_enabled = false`. Sem migração destrutiva.

### Compatibilidade
- Nenhuma coluna renomeada ou removida.
- Nenhum contrato de server fn alterado.
- Nenhuma alteração em RLS ou GRANTs.
