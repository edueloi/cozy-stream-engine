# 1.3.9 — Prospecção pronta para piloto (mesma tela, drawer, unknown ≠ disqualified)

## Causa raiz
1. **Resultados fora da tela.** Ao concluir a Nova Prospecção, o form
   navegava para `/prospecting?openSearch=…` (aba Histórico). O vendedor
   precisava sair da tela para trabalhar com a busca recém-concluída.
2. **`unknown` tratado como `disqualified`.** O engine (`universal-icp-engine.ts`)
   colocava o mesmo critério em `missing_criteria` **e** `disqualifying_reasons`
   sempre que a regra era `required=true` — mesmo sem o dado ter sido enriquecido.
   Resultado: empresas sem CNAE/situação apareciam com "0% + desqualificado".
3. **`Pré-Score` afundava com pendências.** Regras `requires_enrichment` sem
   dado ainda iam ao denominador em modo `final`, arrastando o score para 0.
4. **Sem detalhe do prospect.** Só era possível ver os dados completos após
   importar como Lead.

## Correção (aditiva, sem migration)

### Engine (`src/lib/icp/universal-icp-engine.ts`)
- Novo estado 4-way por critério: `matched | not_matched | unknown | disqualified`.
- Regra: dado ausente **sempre** vira `unknown` (nunca `disqualified`).
  `disqualified` só quando o dado está presente **e** bate regra proibida/negativa
  comprovada, ou quando o critério é `disqualifying=true` e o dado presente não atende.
- `required=true` sozinho **não** desqualifica; só reduz score se o critério
  for pontuado. `disqualifying=true` continua sendo o único caminho para
  reprovação por regra.
- `requires_enrichment` (ou campo fora de `BASIC_ICP_FIELDS`) com dado
  ausente vira `unknown + pending_enrichment` — **não entra no denominador**.
- Novos campos no output: `evaluations[]`, `has_pending_enrichment`,
  `insufficient_data`. Campos legados (`matched`, `missing`,
  `disqualifying`) continuam preenchidos, agora derivados dos estados
  normalizados — sem duplicação entre listas.

### Mapper único (`src/lib/icp/display-mapper.ts` — novo)
- `mapIcpEvaluationForDisplay(score, { minimumScore, enrichmentFinished })`
  agrupa em `matched / not_matched / unknown / disqualified / pending_enrichment`
  e deriva um `summary_label`: `Lead Bom | Em revisão | Fora do perfil |
  Em processamento | Dados insuficientes`.
- `classifyPersistedScore(row)` classifica `prospecting_company_scores`
  para exibição em abas. Frontend **não** monta essas listas mais.

### UI da Nova Prospecção
- `src/routes/_authenticated.prospecting.tsx` — novo `NewProspectionWithResults`
  container que segura `currentSearchId` + `currentIcpId` + `minimumScore`.
  Sem redirecionar para Histórico.
- `src/components/simplified-new-prospection.tsx` — aceita
  `onSearchComplete(searchId, ctx)`. Fallback legado preservado quando o prop
  não é passado.
- `src/components/prospecting-results-panel.tsx` (novo) — abas
  **Leads Bons** (default) · Em revisão · Em processamento · Fora do perfil ·
  Todos, com contagem, seleção, importar Leads Bons / selecionados /
  Bons+Em revisão. Auto-scroll para `#prospecting-results`.
- `src/components/prospect-detail-drawer.tsx` (novo) — Sheet lateral com
  Dados da empresa, Qualificação (Score ICP + Data Quality separados,
  matched/unknown/disqualified sem duplicação), Decisores, Enriquecimento
  (Admin/SuperAdmin vê fontes/custo; vendedor vê apenas "Dados verificados
  pelo JCS Data Engine"). Ações: Importar como Lead, Re-enriquecer,
  Buscar decisor. Reutiliza `listDecisionMakers`, `enrichSelected`,
  `findDecisionMakers`, `importResults` — nenhum server function novo.

Novos testes cobrem:
- Campo ausente → `unknown` (nunca `disqualified`).
- Campo presente que não atende → `not_matched`.
- Regra proibida comprovada → `disqualified`.
- `requires_enrichment` em modo preliminary não reduz denominador.
- Nenhum critério em mais de um bucket.

## Risco de regressão
**Baixo.**
- Engine mantém campos legados (`matched`/`missing`/`disqualifying`)
  preenchidos; caller antigo (`icp.functions.ts::scoreResults`) continua
  operando sem mudança.
- Fluxo legado (Casa dos Dados direto, sem flags) e Smart Flow permanecem
  intocados. Failover 1.3.8 e enriquecimento Kipflow também.
- Leads, CRM, Cadências, WhatsApp, Agenda, E-mail, Billing, Marketplace,
  provider credentials e prioridades → nenhum arquivo tocado.

## Fora do escopo desta entrega
Documentado como próximos passos — deliberadamente evitados para não
desestabilizar o piloto:
- Loop meta-driven multi-lote no `runSearchInternal` (item 8 do brief).
  O `SimplifiedNewProspection` **já** interrompe cedo quando `good >= targetGood`;
  paginação automática entre lotes é ampliação futura.
- Enum de status progressivo em `prospecting_results.status`
  (`searching → pre_scored → enriching → …`). Hoje continua o vocabulário
  atual (`new | enriched | imported`) — abas usam `classifyPersistedScore`
  para inferir estágio sem migration.
- Ambos serão tratados em release próprio com migration aditiva.

## Roteiro manual — Bruna (5 min)
1. Prospecção → Nova Prospecção. Escolha Produto + ICP, UF=SP, CNAE de advocacia
   (6911-7/01), meta=3, máx=10.
2. Clique "Executar". Espere o progresso concluir.
3. **Verifique:** o formulário recolhe e a seção "Resultados da Prospecção"
   aparece **abaixo**, sem sair da tela. Aba padrão = **Leads Bons**.
4. Clique numa empresa. **Verifique:** drawer lateral abre com dados
   completos. Campos vazios (ex.: CNAE não enriquecido) aparecem em
   "Ainda desconhecidos" — **não** em "Desqualificadores".
5. Feche o drawer. Clique "Editar critérios e pesquisar novamente" se quiser
   ajustar filtros. Se rodar de novo, resultados anteriores só somem quando
   a nova busca começar.
6. Selecione 2 empresas e clique "Importar selecionados". Elas aparecem em
   `/leads` sem iniciar cadência automaticamente.
7. Aba Histórico continua funcionando normalmente para buscas antigas.
