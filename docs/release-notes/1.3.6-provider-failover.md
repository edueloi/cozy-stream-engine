# Release 1.3.6 — Provider Failover e Orquestração Inteligente

## Objetivo
A prospecção nunca para porque um provider falhou. O vendedor não sabe qual provider foi usado. O sistema decide sozinho, tenta o próximo em falha recuperável e só encerra quando toda a cadeia falhar.

## Escopo
Alteração isolada ao **Provider Registry** e ao **Enrichment Orchestrator**. Não afeta ICP, Pré-Score, Score Final, Smart Flow, JCS Data Engine (fluxo), Cadências, Leads, WhatsApp, Agenda, Email, CRM ou Agentes.

## Arquivos novos
- `src/lib/providers/failover-classifier.ts` — classifica erros em 15 categorias, decide se dispara failover e sanitiza logs.
- `src/lib/providers/health-score.server.ts` — health 0–100 por org/provider (sucesso, latência, timeout, rate limit, saldo) com cache 60s.
- `src/lib/providers/failover-registry.server.ts` — seleção automática. Filtra por enabled, capability, credencial e budget; ordena por prioridade → health → latência.
- `src/lib/providers/failover-executor.server.ts` — `runWithFailover()` percorre candidatos, tenta próximo em falha elegível, registra `fallback_chain[]`, aborta em erro de usuário (400/422).
- `src/lib/providers/__tests__/failover-classifier.test.ts` — 14 casos (400/422/401/403/402/429/5xx/timeout/dns/ssl/payload/unknown + sanitização).
- `src/lib/providers/__tests__/failover-executor.test.ts` — 5 cenários (primeiro OK, 403→segundo OK, 400 aborta, todos falham, empty→próximo).

## Arquivos não alterados (protegidos por escopo)
- `smart-flow.server.ts`, `universal-icp-engine.ts`, `validate.ts`, `orchestrator.server.ts`, `prospecting.functions.ts` na parte de negócio.
- APIs públicas dos server functions permanecem idênticas.

## Nova ordem de prioridade padrão (configurável)
`company_search`: Kipflow → Casa dos Dados → Apify → API Própria → Webhook. A ordem final vem de `provider_credentials.priority` ASC; a lista acima só é usada como default quando não configurada. **Nunca** hardcoded no fluxo.

## Critérios de elegibilidade (antes de qualquer HTTP)
1. `enabled = true`
2. capability suportada por `PROVIDER_CAPABILITIES`
3. credencial resolvida (`apiKey` presente)
4. `status` diferente de `invalid*` / `error*`
5. budget diário/mensal disponível (`checkBudget`)

Ordenação: `priority ASC → health DESC → avg_latency_ms ASC`.

## Falhas que disparam failover
`invalid_credentials`, `invalid_permission`, `insufficient_balance`, `rate_limited`, `provider_unavailable`, `timeout`, `network_error`, `http_5xx`, `connection_refused`, `dns_error`, `ssl_error`, `maintenance`, `unsupported_capability`, `provider_disabled`.

## Falhas que NÃO disparam failover
`400`, `422`, `invalid_payload`, `invalid_icp` — erro pertence ao usuário; cadeia é abortada e o erro é devolvido.

## Logs
Cada tentativa persiste em `provider_usage_events.metadata`:
- `fallback_chain[]` (providers na ordem tentada)
- `capability`, `attempts`, `duration_ms`, `error_code`, `credential_source`, `reason`

Nunca são gravados: `Authorization`, `Bearer`, `api-key`, `x-api-key`, `secret`, `token`, `password` — redigidos por `sanitizeForLog`.

## Erro amigável quando tudo falha
`friendlyFailoverMessage()` → `"Nenhum provedor disponível para essa busca. Peça ao administrador para revisar as integrações."`
`adminFailoverBreakdown(result)` → lista `[{ provider, reason }]` para o painel do admin (sem stacktrace).

## Como integrar em call-sites existentes
```ts
import { runWithFailover, friendlyFailoverMessage } from "@/lib/providers/failover-executor.server";

const r = await runWithFailover<Company[]>({
  organizationId: ctx.organizationId,
  capability: "company_search",
  operation: "prospecting.search",
  exec: async (cand) => callProvider(cand.provider, cand.config, params),
});
if (!r.ok) throw new Error(friendlyFailoverMessage());
return r.data;
```
O adapter recebe `RuntimeConfig` já resolvido (org → plataforma → env), então continua compatível com a Central Multi-Tenant (release 1.3.2).

## Riscos
- Nenhum schema alterado; sem migrations destrutivas.
- Adapters existentes (Kipflow, Casa dos Dados, Apify) continuam funcionando pelos caminhos legados até serem migrados para `runWithFailover`.
- Health score depende de janela de 30 min de eventos; org sem histórico começa em 80 (neutro) e converge conforme uso real.

## Rollback
Não usar `runWithFailover` no call-site — o caminho legado (chamada direta ao adapter) permanece intacto. Nenhum dado precisa ser revertido.

## Compatibilidade
- Central Multi-Tenant (1.3.2): mantida — o executor lê credenciais via `getProviderRuntimeConfig`.
- Data Engine (1.3.x): mantida — `registry.server.ts` continua exportando `companyEnrichment` e `findDecisionMakers` com a mesma assinatura.
- UI de Integrações (1.3.4): mantida — os campos `enabled`, `priority`, `daily_limit`, `monthly_limit` já são lidos pelo executor.
